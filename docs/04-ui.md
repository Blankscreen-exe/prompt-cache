# 04 · UI (Textual)

A single Textual app. The main surfaces are the **search palette**, the **fill form**, the **prompt editor** and
the **conversation view**. It should feel like a command palette — Raycast, or VS Code's `Ctrl+P` — rather than a
document manager.

## Look and feel

- Clean, dense, calm. Dark theme by default, light theme available, toggled in settings.
- One accent colour, used for selection and the active field only.
- **Fast.** No spinners anywhere on the primary path. Search must feel instant while typing.
- Every action has a **binding shown in the footer**, contextual to the current screen.
- Mouse works — Textual gives clickable rows, buttons and scrollbars for free — but is never required.

Styling lives in a Textual CSS file (`app.tcss`), not inline, so the theme is one file to change.

```
│  PROMPTS                                                                      │

│   "Hiring: senior React developer…"                 1 fill  · 5d ago          │
├───────────────────────────────────────────────────────────────────────────────┤
│ ⏎ use  ^e edit  ^p pin  ^n new  ^t trash  ↑↓ move  esc clear  ^q quit         │
└───────────────────────────────────────────────────────────────────────────────┘
```

- Results grouped **Prompts** then **Conversations**, keyboard-selectable, clickable.
- A prompt row shows: title, kind (plain / template), blank count, includes, pin star, use count.
- A conversation row shows: label, fill count, relative time.
- No match → a single row **"Create prompt: *lin com*"**, `Enter` opens the editor (F2).
- Empty query → Pinned, then Recent, then Most used.

Widgets: `Input` for the box, `OptionList` or a custom `ListView` for results, `Footer` for bindings.

## Screen 2 · Fill form

```
┌ LinkedIn comment ────────────────────────────────── new conversation ────────┐
│ POST         from clipboard ┌──────────────────────────────────────────────┐ │
│                             │ Excited to share that our team just shipped  │ │
│                             │ a new onboarding flow that cut signup drop…  │ │
│                             └──────────────────────────────────────────────┘ │
│ PERSONA      default        [ @agency-info            ▾ ]                    │
│ PROOF        default        [ none                    ▾ ]                    │
│ ANGLE        default        [ add a counterpoint      ▾ ]                    │
│ INCLUDES                    @social-voice ▸                                  │
├─ preview ────────────────────────────────────────────────────────────────────┤
│ Write a LinkedIn comment on the post below. Under 80 words.                  │
│ No hashtags, no emojis, no "Great post!". Lead with the point.               │
│ ‹social-voice›                                                               │
│ ‹agency-info›                                                                │
│ ANGLE: add a counterpoint                                                    │
│ POST: Excited to share that our team just shipped…                           │
├──────────────────────────────────────────────────────────────────────────────┤
│ ^⏎ copy   tab next field   ^v paste into field   ^e edit template   esc back │
└──────────────────────────────────────────────────────────────────────────────┘
```

- One input per blank, by type: `TextArea` for text, `Select` for choices and choice-of-block.
- A **source badge** per field: *from clipboard*, *from conversation*, *default*, or blank if typed.
- The **first empty field is focused**. If everything is pre-filled, focus goes to the copy action so the whole
  flow is one keypress.
- Live preview updates as you type, scrollable, with filled values subtly highlighted.
- Static includes are listed and expandable, not editable here — `Ctrl+E` jumps to the block.
- After copying: a toast, *"Copied · saved to conversation"*, which stays briefly and can be clicked to open it.

**Binding notes.**

- `Ctrl+Enter` is the confirm everywhere, because plain `Enter` must insert a newline inside a `TextArea`. Plain
  `Enter` also confirms when focus is on a `Select` or a button.
- Textual binds `Ctrl+P` to its own command palette by default, which collides with pin. The app sets
  `ENABLE_COMMAND_PALETTE = False` — this app *is* a palette, so a second one would only confuse. Found while
  verifying M0; there is a regression test for it.
- **Textual's `Input` and `TextArea` both bind `Ctrl+E` and `Ctrl+D` themselves** (end-of-line and
  delete-character). A screen binding on the same key does nothing at all unless it is declared
  `priority=True` — it fails silently, with no error. Screen bindings on the search palette are therefore all
  `priority`. Found at M1, where `Ctrl+E` (edit) had been quietly dead; `TestBindingsAreNotShadowed` guards it.
- **Never name a Screen attribute `_closing`.** Textual's `MessagePump` owns it, and assigning to it tells the
  widget its message pump is shutting down — the app then hangs with no error and no traceback. The same risk
  applies to `_running`, `_message_queue` and friends. `TestFrameworkAttributeCollisions` guards the screens
  against this; it cost an afternoon at M5 to find.
- Textual's `TextArea` highlighting is tree-sitter based, and `register_language` needs a **compiled grammar**, so
  colouring `{{blanks}}` is not a few lines. The editor uses the bundled **markdown** highlighting instead, and
  reports structure (blanks, includes, missing blocks, "used by N") in its meta line, which is more useful than
  colour anyway.
- Deleting a prompt lives on the search screen, **not** in the editor: `Ctrl+D` means "delete character" inside a
  `TextArea`, and a destructive action must never share that key.

## Screen 3 · Prompt editor

- A `TextArea` for the body with **syntax highlighting for `{{blanks}}`, `{{@includes}}` and `#tags`**.
  - Textual's `TextArea` highlighting is tree-sitter based, so custom `{{…}}` highlighting needs either a small
    custom language definition or a simpler overlay. **If it proves awkward, ship M1 without highlighting** and
    add it in M2 — it is a nicety, not the product.
- A side panel showing:
  - detected blanks with their resolved types
  - includes, with a warning for any that are missing or cyclic
  - tags, **"used by N templates"**, pin state, version history
- **Autosave** with a subtle saved indicator. No save button.
- Bindings: fill, copy raw, history, duplicate, delete.

## Screen 4 · Conversation view

- Header: label (editable), created time, templates used so far.
- **Values** panel: every blank name the conversation knows, each editable, each with *set from clipboard*.
- **Timeline** of fills: template name, time, and the assembled output — expandable and copyable.
- Actions: **Continue with…** (template picker), **save value from clipboard** (`Ctrl+S`), archive, delete.

## Interaction requirements

- **Keyboard:** everything reachable, focus always visible. `Esc` steps back one level.
- **Mouse:** every row, field and action clickable.
- **Clipboard:** reading and writing must work on Windows and Linux (see 05-architecture.md). Every field also has
  a manual paste binding as a fallback, so a broken clipboard degrades the app rather than breaking it.
- **Terminal sizes:** usable from roughly 80×24 upward. Panels collapse rather than overflow on narrow terminals.
- **Pasting large text** into a `TextArea` must work — Textual supports bracketed paste, but it is worth an
  explicit test with a multi-paragraph post on both Windows Terminal and a Linux terminal.
- **No colour assumptions:** respect `NO_COLOR`, and stay legible on both light and dark terminal backgrounds.
